## Организация кода

В проекте реализована модульная структура, разделяющая логику работы с данными, фильтрацию, отображение и управление приложением:

*   **`task-service.js`** — базовый модуль бизнес-логики. Отвечает за CRUD-операции над задачами (создание, добавление, удаление, переименование, изменение статуса), валидацию входящих данных и расчет общей статистики.
*   **`task-selectors.js`** — модуль фильтрации. Содержит функцию с чистой логикой отбора задач в зависимости от переданного фильтра, не изменяя исходные данные.
*   **`task-view.js`** — модуль отображения (представления). Отвечает за генерацию DOM-элементов карточек задач, рендеринг списка в интерфейсе, обновление текстовой сводки и переключение состояния пустых экранов.
*   **`main.js`** — главный координирующий модуль приложения. Инициализирует начальное состояние, связывает DOM-элементы с обработчиками событий и управляет глобальным циклом перерисовки интерфейса (`renderApp`).

## Отладка и клавиатура

**1. Точки останова и исследование контекста события:**
Отладка производилась в функции `handleTaskListClick(event)` модуля `main.js`. Точка останова была установлена на строке преобразования идентификатора карточки: `const id = Number(card.dataset.taskId);`.

При клике по кнопке смены статуса задачи с `id = 4` были зафиксированы следующие значения переменных:
*   `event.target`: Ссылка на элемент `<span>` с классом `action-label` (или саму кнопку `<button>`), по которому непосредственно пришёлся клик мыши.
*   `event.currentTarget`: Ссылка на элемент `<ul>` с `id="task-list"`, на который назначен постоянный слушатель событий (делегирование).
*   `card.dataset.taskId`: Строковое значение `"4"` (тип *String*), извлечённое из HTML-атрибута `data-task-id`.
*   `id`: Числовое значение `4` (тип *Number*), полученное после принудительного приведения типа.
*   `action`: Строка `"toggle"`, полученная из `button.dataset.action`.
*   `Результат сервиса`: Объект `{ ok: true, tasks: [...] }`, где в массиве `tasks` у целевого объекта изменилось поле `completed`. Новый массив успешно заменил старую ссылку в переменной `currentTasks`

**2. Проверка клавиатурной доступности и фокуса:**
*   **Взаимодействие:** Клавиша `Tab` последовательно и предсказуемо перемещает фокус по интерактивным элементам страницы (сначала по кнопкам верхних фильтров, затем заходит внутрь карточек задач, перемещаясь по кнопкам действий). Нажатие клавиш `Enter` и `Space` (Пробел) на сфокусированной кнопке успешно эмулирует клик мыши: активирует фильтр, меняет статус или удаляет задачу.
*   **Положение фокуса после изменения статуса:** При нажатии кнопки «Выполнена» (`action === "toggle"`) карточка обновляется, но благодаря функции `restoreTaskFocus(id, action)` фокус программно возвращается на точно такую же кнопку пересозданной карточки. Пользователь может продолжить управление с клавиатуры без потери позиции.
*   **Положение фокуса после удаления:** При нажатии кнопки «Удалить» карточка полностью уничтожается из DOM-дерева. Так как старый элемент фокуса исчез, срабатывает запасной сценарий функции `restoreTaskFocus`: фокус автоматически и безопасно переводится на кнопку текущего активного фильтра вверху страницы.

**3. Тестирование отказоустойчивости при подмене атрибутов:**
В панели *Elements* встроенного отладчика были проведены контролируемые изменения HTML-кода карточек для проверки защитных механизмов приложения:
*   **Случай 1 (id = 777):** Атрибут `data-task-id` был изменен на несуществующий в системе числовой идентификатор `"777"`. При попытке удаления данной задачи код успешно отработал валидацию на стороне сервиса. В блоке `#operation-message` появилось текстовое предупреждение: *«id задачи не существует в списке задач»*. Глобальный массив данных приложения при этом остался нетронутым.
*   **Случай 2 (id = 4abc):** Атрибут был изменен на некорректную строку `"4abc"`. При попытке переключения статуса встроенная проверка `Number.isSafeInteger(id)` в `main.js` вернула `false`. Выполнение функции прервалось до вызова бизнес-логики, а в интерфейс мгновенно вывелось сообщение: *«некорректный id»*.

При любом последующем переключении верхних фильтров (например, клике на вкладку «Все») приложение берет данные из чистого внутреннего массива `currentTasks` и полностью перерисовывает интерфейс, восстанавливая исходные корректные ID карточек в DOM и полностью стирая сообщения об ошибках.

## Вывод

В ходе выполнения лабораторной работы были освоены принципы проектирования современных интерактивных веб-приложений на чистом JavaScript с использованием модульной архитектуры.

### Основные результаты:
1.  **Модульное разделение ответственности:** На практике реализован паттерн, разделяющий бизнес-логику работы с массивом данных (`task-service.js`), чистые функции фильтрации и селекции (`task-selectors.js`), а также механизмы рендеринга и работы с DOM (`task-view.js`). Это позволило сделать код масштабируемым и независимым от окружения (методы сервиса тестируются в Node.js, а вью — в браузере).
2.  **Иммутабельность данных:** Все операции по добавлению, удалению и обновлению задач реализованы без прямой мутации исходного состояния (через методы `map`, `filter` и деструктуризацию массивов `[...tasks]`). Это гарантирует предсказуемость состояния приложения, исключает побочные эффекты и позволяет легко отслеживать изменения.
3.  **Отказоустойчивость интерфейса:** Реализована строгая валидация входящих параметров и идентификаторов на стыке взаимодействия DOM и JS (обработка невалидных ID вроде `777` или `4abc`).
